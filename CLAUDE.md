# Repository Automation Rules

These rules apply to GitHub Actions and releases in this repository. The source
of truth for the Windows build is `.github/workflows/release-windows.yml`; also
follow the release runbook in `docs/i0001_windows-remote.md`.

## GitHub Actions

- Pin every third-party action to a full immutable commit SHA. Add a trailing
  comment with the corresponding release tag, or the branch and pin date when
  the action has no meaningful release tag.
- When changing an action, check its upstream releases/tags and use the latest
  stable compatible version. Do not blindly copy an old pin from another repo.
- Actions must use a currently supported GitHub Actions runtime (Node.js 24 or
  newer). Do not hide deprecation warnings with force/compatibility flags.
- If no supported action version exists, prefer a small explicit installation
  step. Pin downloaded tool versions and verify their published SHA-256 before
  executing them.
- Keep permissions minimal. The release job requires only `contents: write`.
  Keep checkout credentials disabled unless a step demonstrably needs them.
- Preserve `fetch-depth: 5` (or greater) on the repository checkout. Release
  note generation requires up to five commits to be available locally.
- Continue to fetch upstream herdr from the release tag in
  `patches/herdr/BASE`, verify its peeled commit against
  `patches/herdr/BASE_COMMIT`, then apply `patches/herdr/*.patch` in lexical
  order. Do not build from upstream `master`.
- Avoid noisy but preventable Git warnings. In particular, fetch annotated
  upstream tags explicitly rather than shallow-cloning with `--branch`.
- Before committing workflow changes, run:

  ```bash
  git diff --check
  go run github.com/rhysd/actionlint/cmd/actionlint@latest \
    .github/workflows/release-windows.yml
  ```

- A workflow is not considered clean merely because it succeeded. Inspect its
  annotations and logs, and fix warnings and deprecations rather than ignoring
  them.

## Numbered release creation

- Numbered releases are generated by GitHub Actions, not assembled or uploaded
  manually. Pushing a matching tag triggers the build and publication.
- Release tags use `vX.Y.Z-win.NN`. `vX.Y.Z` must exactly equal the value in
  `patches/herdr/BASE`. Number each upstream version independently: start at
  `01` whenever `vX.Y.Z` changes, then increment the highest existing `NN` for
  that same upstream version. Always use two decimal digits (`01` through
  `09`, then `10`, and so on) so GitHub's lexical release ordering is correct.
- Tag only a clean, pushed, synchronized `master`. The tag must point to the
  commit intended to appear as `repo_commit` in `BUILD_INFO.txt`.
- Never move or overwrite a published tag. If another commit must be included,
  increment `N` and create a new release.
- Use the documented sequence:

  ```bash
  git fetch origin --prune --tags
  test -z "$(git status --porcelain)"
  test "$(git rev-parse HEAD)" = "$(git rev-parse origin/master)"
  git tag vX.Y.Z-win.NN
  git push origin vX.Y.Z-win.NN
  gh run watch --exit-status <run-id>
  ```

- `workflow_dispatch` publishes or refreshes the rolling
  `windows-remote-latest` prerelease. Use a numbered tag for a durable release.
- If release-workflow changes are committed after a tag was published, create
  a new numbered tag when the release is expected to represent the repository
  tip. Do not retarget the old release.

## Release notes

Every release body must be generated by the workflow and contain:

1. A short description of the native Windows build and pinned upstream base.
2. A prominent `Repository commit` link for the exact `GITHUB_SHA` built.
3. `Recent repository commits (up to 5)`, newest first. Each item must include
   the short SHA linked to the full commit and the commit subject.
4. A pointer to `BUILD_INFO.txt` for upstream/patched commits and artifact
   SHA-256 checksums.

The list must contain no more than five commits. Keep release-note generation
in the workflow for both creation and editing so reruns do not leave stale
notes.

## Post-release verification

After every numbered release:

- View it by explicit tag (`gh release view <tag>`); the default lookup may
  omit prereleases.
- Confirm the release target and `BUILD_INFO.txt` `repo_commit` equal
  `git rev-parse <tag>`, and `BUILD_INFO.txt` `upstream_commit` equals
  `patches/herdr/BASE_COMMIT`.
- Confirm `herdr-windows-x86_64.exe`, `hcode`, and `BUILD_INFO.txt` are present.
- Confirm the workflow conclusion is `success`, check-run annotations are
  empty, and logs contain no warning/deprecation messages.
- Report the release URL, workflow-run URL, tag, and repository commit.
